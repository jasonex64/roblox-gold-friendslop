# EXP-001 — Gate B cooperative validation (T-022)

## Hypothesis and expected result (recorded before validation)

Another player improves the operation through shared dirt handling, sales and
sluice funding, while a solo player can complete the same loop. Expect no money
or inventory duplication, a single funded machine, shop-only payment, and clean
bell/replay resets. Automated correctness cannot establish enjoyment or useful
cooperation; those require human observations and an explicit decision.

## Baseline and scope

Merged main `2ec6c95`; rulesVersion `gate-b-crew-prototype`. Use the existing
`t011-alerts-playtest.rbxl` only, synced from this repository. D-032 caps crews at
four; D-033/D-034 define the base bin and defer upgrades; D-035/D-036 define the
funded sluice and Bucket-to-sluice-to-Backpack transfer. Read all numerical
expectations from `src/shared/Config.luau`; this experiment changes no tuning.

## Proposed human plan — approval pending

Run fresh solo, two-, three- and four-person sessions using actual humans and
clients. Record tester names, platform, crew size, whether a client is human
controlled, assistance and build. A single person driving multiple clients is
an interface test, not independent cooperative feedback.

For each crew size:

1. Start together; dig, sift and sell. Note first-sale clarity and each wallet's
   share versus Crew Haul. Buy a tool and confirm spending leaves Haul unchanged.
2. Deposit and withdraw shared dirt with selected quantities and All. Have a
   teammate process another player's dirt; check full/empty behavior and clarity.
3. Earn funding normally, contribute from personal wallets, and have different
   players try the final payment. Build once, Quick Transfer Bucket dirt, observe
   processing/stats, collect into Backpack and sell. Try full Bucket, Backpack
   and sluice limits; uncollected output must not sell directly.
4. Test a departure and late join/rejoin. Deposited dirt and sold Haul remain;
   late arrivals wait for the next run. Observe AFK warning/pause and resume by
   qualifying production, without counting passive/UI activity.
5. Reach the natural bell with unsold/unfinished inventory. Confirm it creates
   no payment. Vote replay, including a pending voter leaving; confirm a fresh
   run with empty inventory, zero cash/funding and no built sluice.
6. Describe a specific way another player helped or hindered, whether solo was
   viable, confusing controls, desire to retry, and any failure. Record first
   sale/build times and final Haul if observed; never estimate missing values.

After all sizes, yukicide gives an explicit **continue** or **revise** decision,
with reasons and any blocking issues. Missing runs remain pending. Existing
individual payout/bin/sluice approvals are supporting evidence only.

## Automated validation plan

Run all repository gates and strict number validation. Inspect/run pure cases
for crews through the cap, roster locking/join/leave, AFK boundaries, competing
sales/contributions/transfers, capacity, exact cutoff and repeated requests.
Run existing Crew, Bin, Machinery and Shift Studio fixtures in the same place;
label injected clocks/cash, synthetic recipients and real client counts.
These isolated server fixtures do not measure human usefulness or natural-run
fundability. Capture the exact relied-on console lines and any failures.

### Automated evidence, 2026-10-24

- Repository baseline: 102 unit tests passed, format/lint/build and runner
  self-test passed; strict numbers reports zero provisional values.
- Pure tests cover crew sizes one through four, roster locking/overflow/rejoin,
  fair remainder conservation, AFK boundaries, competing final contributions,
  full storage, simultaneous collectors, rollback and exact cutoff/reset.
- Same-place solo Studio: Crew, Bin, Machinery and Shift fixtures passed.
  Crew uses one real avatar plus three synthetic recipients; the others use
  one avatar. All use isolated controllers and injected clocks/data.
- A requested four-client session initially produced three connected avatars;
  Bin and Machinery then failed station checks with test avatars remaining
  airborne. A requested additional client connected, but the original three
  disconnected. That attempt is **inconclusive**, not a four-client pass or a
  confirmed gameplay defect. Ended that temporary test.
- Fresh two-client session from the same place: Bin and Machinery passed, as
  did `tests/studio/GateB.luau`. The new fixture dispatches deferred competing
  server-handler calls: sales consume each inventory once, retries/empty sales
  preserve money, competing full-price contributions charge only one price,
  and exact-cutoff sale/contribution/transfer requests reject before heartbeat.
  The fixture accepts two through the approved cap and prints the actual count.
  It does not claim network scheduling, human input or earned funding.
- In the fresh session, added clients individually and waited for grounded
  avatars. Player3/Player4 correctly remained queued after the live roster lock.
  Bin, Machinery and GateB then all passed with **four actual connected Studio
  clients**, using isolated fixture rosters that admitted all four. This supplies
  cap-sized transaction evidence; it does not turn the live late arrivals into
  admitted crew or claim a natural four-human run. Initial startup failures are
  retained above for reproducibility.
- Controlled live departure of admitted Player1 kept Player2 admitted and the
  late arrivals queued; server remained responsive without a new script error.
  Repeated Bin, Machinery and GateB with the remaining three actual clients:
  all passed. Thus Bin/Machinery cover 1/2/3/4 actual avatars and contention
  covers 2/3/4. Ended the temporary test, preserving the original edit place.

No product behavior or tuning changed. Human evidence and the milestone exit
decision remain pending; a passing fixture is not approval to close Gate B.
