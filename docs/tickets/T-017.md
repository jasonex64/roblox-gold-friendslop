## Goal
`src/shared/Pure/Run.luau` owns run phases and the end/reset order, so T-005 and T-009 only wire it to the server clock.
Source: DESIGN §4, 12-13, 15 (Gate A).

## Why
Who uses it: T-005, T-009.
What breaks without it: end-of-run ordering bugs (double sale, carried state) are untestable in Studio.

## Acceptance criteria
- [x] `new(runId, now, config)` waits for the ready condition, then runs until `start + shiftSeconds`; `accepts(run, now)` is false outside running — test: RUN-SM-1
- [x] `finish(run)` returns ordered steps: stop production, sell completed, discard unprocessed, freeze result; calling twice errors — test: RUN-SM-2
- [x] `reset(run)` returns a fresh run with a new id and no carried values — test: RUN-SM-3

Done: added src/shared/Pure/Run.luau and tests/unit/Run.spec.luau. Lifecycle is waiting -> countdown -> running -> ended -> results -> reset. Server-supplied readiness starts a configured countdown; losing readiness before launch restarts it. Shift boundaries are scheduled from readiness/countdown, not tick arrival. accepts checks the exclusive end cutoff directly even before the next advance. finish emits the four settlement steps once. reset reconstructs a fresh waiting state with a new replay ID and no copied gameplay fields, and retires the old run against repeated reset.
API contract for T-005/T-009: new(runId, now, {readySeconds, shiftSeconds}) snapshots and freezes required timing config; no tuning defaults were introduced. advance(run, now, ready) mutates the retained server run using finite monotonic time and a server-derived boolean ready condition. Call advance before action handling and before finish; readiness is ignored once running. accepts is a read-only check and rejects pre-start, stale, and cutoff-or-later timestamps. finish requires ended, sets results, and returns stop_production, sell_completed, discard_unprocessed, freeze_result in that order. These are instructions for server wiring, not executed economic operations: T-009 must execute them before calling reset and initialize new external inventory/ledger/loadout/counters. Reset retains only copied config and the clock baseline; old gameplay fields are absent. Initial IDs must be unique and reserve their /replay suffix namespace; successive resets append /replay, with each predecessor resettable once. No clocks, Roblox APIs, night/rush phases, inventory systems, or rewards implemented here.
