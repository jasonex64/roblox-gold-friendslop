Signatures for T-040, the sole caller:
- `Progression.new(store, Profile)`. Store: `read(key) -> (ok, value | message)`, `update(key, transform) -> (ok, value | message)` with UpdateAsync semantics. Key: `profile:<userId>`, where userId is `tostring(player.UserId)`.
- `load(userId)` -> `{status = "loaded", profile}` or `{status = "failed", reason = "store_error" | "invalid_profile" | "unsupported_version", message?}`. A default is created only after a successful read finds nothing.
- `store(manifest)` -> `pending` | `alreadyApplied` | `failed`; a conflicting payload for the same (runId, userId) raises an error.
- `pending(userId)` -> `{status = "loaded", profile, manifests}` (runId order) or `failed`.
- `apply(userId, runId)` -> `saved` | `alreadyApplied` | `failed`; a run that is neither pending nor applied raises an error.
- `recordCandidate` shape: `{score, crewSize, assisted, rulesVersion}`.
Recovery policy: no retry loops. A failed `store` means nothing is pending and nothing may be shown as saved. A failed or unacknowledged `apply` leaves the manifest pending, and T-040 applies `pending(userId)` again on the next load. Repeating either call is harmless. Each manifest is written inside its recipient's own profile key in one UpdateAsync, so it stays discoverable after a crash. Markers (about 50 characters per run, roughly 80,000 runs per key) are never pruned.
