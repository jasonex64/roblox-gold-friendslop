## Goal
`src/shared/Pure/Ledger.luau` does all Gate A money math: atomic sale, purchase, Crew Haul, solo wallet.
Source: DESIGN §6-8, 13; D-002, D-003, D-007.

## Why
Who uses it: T-008, T-009.
What breaks without it: money bugs (double sale, haul reduced by spending) land in server code.

## Acceptance criteria
- [x] `sell(ledger, finds, requestId)` marks finds sold once, adds base values to haul and wallet; a repeated requestId changes nothing — test: LEDGER-1
- [x] `buy(ledger, item, requestId)` checks affordability and prerequisites, deducts once, never reduces haul; rejection leaves the ledger unchanged — test: LEDGER-2
- [x] Selling an already-sold or unknown find errors by name — test: LEDGER-3

## Out of scope

- Prices (Config)

Unknown/already-sold/duplicate finds error with the offending ID before any mutation.
API contract for T-008/T-009: ledger contains haul, wallet, finds keyed by ID ({baseValue, sold}), owned item IDs, and successful requests. Only server-verified completed finds enter this registry; baseValue is the final source-adjusted sale amount in the caller's fixed-point integer units. sell takes only find IDs, never prices. buy takes a trusted catalog entry {id, price, prerequisites}; production prices come from Config. Both return (replacementLedger, nil) on success or (originalLedger, namedReason) for replay/purchase rejection. The server must serialize and atomically commit returned state and synchronize its batch sold state; do not run multiple operations against a stale ledger. Request IDs share one namespace across sell/buy for the run, so a replay with changed payload or operation grants nothing. Rejected buys do not consume the ID. Empty sales grant nothing and record the request; no activity tracking is implemented here. No prices, crew splits, contributions, or wiring added. The IEEE-754 safe-integer bound is a numeric representation constraint, not a gameplay tuning value.
